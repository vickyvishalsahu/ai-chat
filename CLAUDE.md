# ai-testing

A multi-conversation AI chat playground: React SPA talking to a Fastify server over Connect-RPC, with replies streamed from Groq and conversations stored in Postgres.

## Layout

- `packages/proto` - the `ChatService` schema (`proto/chat/v1/chat.proto`). Code in `src/gen` is generated by `buf` on every `pnpm install` and is gitignored. Edit the `.proto`, then `pnpm --filter @ai-testing/proto generate`.
- `apps/server` - Fastify + `@connectrpc/connect-fastify`, Drizzle ORM. `src/connect/chat.ts` holds all chat logic; `src/compose.ts` is the one place that picks real vs stand-in dependencies.
- `apps/web` - Vite + React 19 + React Router 8 + TanStack Query + Tailwind v4. Feature-sliced: thin `src/routes`, logic in `src/features/chat`, cross-cutting code in `src/shared`. `@/*` maps to `src/*`.
- `api/[[...path]].ts` - Vercel serverless entry that feeds requests into the same Fastify app.

## Commands

- `pnpm dev` - server on :3001, web on :5173 (Vite proxies `/api` to the server)
- `pnpm test` - server (node:test) and web (Vitest) unit tests
- `pnpm test:e2e` - Playwright, boots both servers itself
- `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm build`
- `pnpm --filter @ai-testing/server db:generate` / `db:migrate` - Drizzle migrations

## How the chat works

`ChatService` has three RPCs: `ListConversations`, `GetConversation`, `SendMessage` (server-streaming). There is no create RPC: `SendMessage` upserts the conversation from a client-generated UUID. `GetConversation` on an id nothing was sent to returns `NotFound`, which the web app treats as an empty thread, not an error.

`SendMessage` streams three kinds of response: `user_message` once (the persisted user message), `content_delta` per token, `final_message` once on success. Whether `user_message` arrived decides what the client does on failure: before it, the send is rolled back; after it, the user's message stays and only the assistant reply failed. Keep that contract when changing either side.

On the web side, `useSendMessage` owns streaming state. It keeps an `overlay` of locally known messages that the thread de-duplicates by id against the TanStack Query cache, so messages never flicker while the cache catches up.

## Dependencies and credentials

Every external dependency sits behind a small interface with a real and a stand-in adapter, chosen in `apps/server/src/compose.ts`:

- Postgres: Neon when `DATABASE_URL` is set, otherwise in-memory PGlite running the same migrations
- LLM: Groq when `GROQ_API_KEY` is set (model `openai/gpt-oss-120b`), otherwise `FakeGroqClient`; `CHAT_GROQ_MODE=fake` forces the fake
- Rate limiting: Upstash when `UPSTASH_REDIS_REST_URL`/`TOKEN` are set, otherwise disabled

Outside production, missing credentials fall back to stand-ins, so `pnpm dev` and every test run with zero setup. With `NODE_ENV=production` all of them are required. The Groq key is server-side only and must never reach the browser.

Migrations are never run automatically. After changing `apps/server/src/db/schema.ts`, run `db:generate`, commit the SQL, then `db:migrate` against Neon.

## Testing conventions

Tests cross the same interface callers use. Server tests call `ChatService` through a real Connect client over `createRouterTransport`, with PGlite and `FakeGroqClient`. Web tests mock only `chatClient`. CI never calls Groq.

## Git

`dev` is the working branch; `main` only changes through `./release dev`. `.husky/pre-push` blocks pushing from `main`. Pre-commit runs lint-staged.
